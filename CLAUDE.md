# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal, single-user, local-only job application tracker (Next.js App
Router + TypeScript). It has no login/accounts and is never deployed — it
runs on `localhost` on one person's machine. Data lives in a local SQLite
file (`data/app.db`), and the AI-generation features (cover letters, resume
bullets, interview questions, company briefs) work by shelling out to the
**locally installed `claude` CLI** as a subprocess instead of calling a
billed API — there is no `ANTHROPIC_API_KEY` anywhere in this app. Keep that
constraint in mind before adding anything that assumes a hosted API client
or multi-user auth.

## Commands

```bash
npm install        # first-time setup
npm run dev         # starts the app at http://localhost:3000
npm run build       # production build
npm run start        # run a production build
npm run lint          # next lint
```

`npm run dev` / `npm run build` automatically run `scripts/init-db.ts` first
(via the `predev`/`prebuild` npm hooks) to create `data/app.db` from
`db/schema.sql` if it doesn't exist yet, and to (re)apply the schema — the
schema uses `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` so
this is safe to run on every start rather than needing a migration tool.

There is no test suite in this repo yet.

The day-to-day launch path for the end user is the **"Job Tracker" desktop /
Start-menu shortcut** → `wscript launcher\launch-tracker.vbs` →
`launcher\launch-tracker.ps1`: starts `npm run dev` hidden (log in
`data\server.log`) unless port 3000 is already up, waits for it (checks both
`::1` and `127.0.0.1` — Next may listen on IPv6 only), opens a Chrome
`--app` window with a dedicated profile (`%LOCALAPPDATA%\JobTracker`), and
kills the server when that window closes — but only if the launcher started
it. Icon: `launcher\job-tracker.ico` + `src\app\icon.png`, generated by
`launcher\make-icon.ps1`. The older `start-tracker.bat` still works.
Because that app window uses its own empty Chrome profile, job-posting links
must NOT be plain `target="_blank"` links: `OpenPostingLink` POSTs to
`/api/open-link`, which launches the real `chrome.exe --profile-directory=…`
(profiles read from Chrome's `Local State`; chosen profile kept in
localStorage, default = Chrome's last-used). The route requires a JSON
content-type so other websites can't trigger it cross-origin. None of
this is relevant when doing dev work here.

## Architecture

**The one thing that requires reading multiple files to understand: the
`claude` CLI is the entire AI backend.** [src/lib/claude-cli.ts](src/lib/claude-cli.ts)
spawns `claude -p --output-format text` and writes the prompt to **stdin**
(never as a CLI argument — job postings/resumes can exceed Windows
command-line length limits, and stdin sidesteps all shell-escaping
concerns). Every feature that "calls AI" — the 4 generation buttons and the
URL/text job-posting parser — funnels through this one `runClaudePrompt()`
function. It throws a typed `ClaudeCliError` with a `code` (`not_found` /
`timeout` / `nonzero_exit` / `empty_output`) that API routes turn into
user-facing error messages. The CLI binary path can be overridden via
`CLAUDE_CLI_PATH` (see `.env.example`) if `claude` isn't on PATH for the Node
process — on this dev machine it's set in `.env.local` to the full path of
the npm-installed shim.

**Windows-specific gotcha (already handled, don't undo it):** npm installs
`claude` as a `.cmd` shim on Windows, and `child_process.spawn(..., {shell:
false})` cannot execute `.cmd`/`.bat` files directly — it fails with
ENOENT/EINVAL even when the path is correct. The naive fix (`shell: true`)
makes Node concatenate the args array into an unescaped shell string, which
is fine here (args are fixed literals, never user input) but still not
ideal. Instead, `runClaudePrompt()` explicitly re-targets the spawn through
`cmd.exe /d /s /c <cli> <args>` when `process.platform === "win32"`,
keeping `shell: false` throughout. If you ever refactor this function,
re-verify a `.cmd`-shimmed CLI still launches on Windows — a bare
`spawn("claude", [...])` will silently fail there.

**Data flow for "Add Job":**
1. URL path: [src/lib/extract.ts](src/lib/extract.ts) fetches the page
   server-side, runs it through `@mozilla/readability` + `jsdom` to strip
   nav/ads/boilerplate down to article text (deliberately non-AI — cheap and
   deterministic), then makes **one** `claude` CLI call asking for strict
   JSON `{title, company, description}` (prompt built in
   [src/lib/prompts.ts](src/lib/prompts.ts)'s `buildExtractPrompt`). This
   returns an editable **draft**, not a saved job — the user reviews/edits
   fields client-side before the actual `POST /api/jobs` create.
2. Paste-text path: skips the CLI entirely — the user types Title/Company
   directly alongside the pasted description (see
   `AddJobFromTextForm.tsx`), since they're already typing by hand.

**Data flow for "Generate":** `POST /api/jobs/[id]/generate` loads the job +
the single-row `profile` (resume text), builds a prompt via
`buildGenerationPrompt()` (one of 4 task-specific templates in
`prompts.ts`, all sharing a common job+resume context block), runs it
through `runClaudePrompt()`, and upserts the result into `generations` via
`saveGeneration()` — the table has `UNIQUE(job_id, type)`, so regenerating
**overwrites** rather than versioning (`INSERT ... ON CONFLICT DO UPDATE`).

**Kanban drag-and-drop** ([src/components/board/Board.tsx](src/components/board/Board.tsx)):
state is `Record<JobStatus, Job[]>`, not a flat list. `@dnd-kit`'s droppable
column ids are the status strings themselves; card ids are job ids. All
reordering/cross-column logic lives in one `handleDragEnd` — it does an
optimistic local update (snapshotting `columns` first) and PATCHes
`{status, position}` to `/api/jobs/[id]`, rolling back the snapshot and
toasting an error if the request fails. Server-side, `moveJob()` in
[src/lib/jobs.ts](src/lib/jobs.ts) fully re-numbers `position` (0..n-1) for
every job in the destination column (and the source column, if different)
on every move — simple full re-index rather than fractional positioning,
which is fine at personal-tracker scale.

**Job Watch (daily web-search discovery):** separate from the hourly
`runScanCycle` connectors. [src/lib/discovery/job-watch.ts](src/lib/discovery/job-watch.ts)
runs three parallel `claude` CLI sessions with `--tools WebSearch,WebFetch`
(via `runClaudePrompt`'s `tools`/`timeoutMs` options — the only callers that
enable tools): priority companies, target companies + broad searches, and
every company already on the board. Each must reply with a `<jobs>[...]</jobs>`
JSON block. `runJobWatch()` in `scanner.ts` dedups by URL *and* normalized
company+title (so already-applied roles never reappear), saves finds to the
top of Wishlist (no auto-generated cover letters — discovered jobs are
never auto-tailored; generation only happens via the Generate buttons). It runs at most once per local calendar
day: the board's `JobWatchBar` POSTs `/api/job-watch` on mount (no-op unless
`isJobWatchDue()`), the "Refresh jobs" button forces a run, and the hourly
instrumentation timer also pings it. The lists live in
`search_preferences.job_watch_*` (newline-separated, edited in Settings →
Discovery); defaults are in `job-watch-defaults.ts`. Adding `job_watch` to
the `discovered_via`/`source` CHECK constraints required a one-time table
rebuild in `scripts/init-db.ts` (it backs up `data/app.db` first).

**Job Watch freshness:** only postings dated within `JOB_WATCH_MAX_AGE_DAYS`
(30, in `job-watch-defaults.ts`) are kept — the prompt asks for exact
`YYYY-MM-DD` dates and `toListing()` drops undated/older results regardless.
`listJobs()` hides Job Watch finds still in Wishlist that are undated or past
that age (`STALE_JOB_WATCH_SQL` — hidden, not deleted; manual jobs are never
hidden — note it must use `discovered_via IS 'job_watch'`, since `= ` against
NULL once hid every manual job), and orders Wishlist by
`COALESCE(posted_at, created_at)` newest first, and Applied alphabetically by
company (then title), so drag-reordering *within* those two columns doesn't
persist (other columns still use `position`). A hidden find
that Job Watch sees again with a newer date gets `refreshPostedAt()` and
reappears. The user prefers company career sites over job boards: the prompt
searches career sites first and must resolve board finds to the company's own
posting URL; `src/lib/job-sources.ts` (`JOB_BOARDS` domain list) drives the
card's "Career site" / "via LinkedIn" label and, via `JOB_BOARD_URL_SQL`,
ranks career-site links above board links within the same posting day.

**KPIs + Referral First:** `referral` ("Referral First") is a status between
Wishlist and Applied for jobs parked until the user talks to a reference.
`jobs.applied_at` (first time a job reached any `APPLIED_STATUSES` stage;
cleared if moved back to Wishlist) and `jobs.status_changed_at` are
maintained by `recordStatusChange()` in `jobs.ts` — every status write path
(`createJob`, `updateJob`, `moveJob`) must call it. Past applications were
backfilled from `created_at` (not `updated_at`: `moveJob` used to bump
`updated_at` on every card in a column; it now only renumbers `position`).
`KpiStrip` computes everything client-side via `computeKpis()` in
`src/lib/kpis.ts` from a job list + `search_preferences.daily_goal` (0 = no
goal). `computeKpis()` also returns pipeline/outcome metrics (`stageCounts`,
`interviewRate`, `offerRate`, `rejectionRate`, `responseRate`,
`avgDaysToResponse` from `applied_at` → `status_changed_at`) and a
`byCountry` breakdown. `KpiStrip` is given both `overallJobs` (Board's
`rawJobs`, every country) and `countryJobs` (the selected country's slice)
and has its own Overall / <country> scope toggle — every tile, including the
to-do lists, is recomputed from whichever one is active via a second
`computeKpis()` call. The toggle only renders when `overallJobs` spans more
than one country; the "By country" tile only renders in the Overall scope.

**Job Watch filters (early-career + sponsorship-required profile; see
`GRADUATION_TERM` / `REQUIRES_SPONSORSHIP` in `job-watch-defaults.ts`):**
`isSeniorTitle()` (`discovery/seniority.ts`) drops Senior/Sr/Lead/Principal/
Staff/Director/level III+ titles from results and hides such finds already in
Wishlist (JS filter in `listJobs()`). The prompt skips no-sponsorship /
citizens-only / clearance / ITAR postings and `NO_SPONSORSHIP_TEXT` backstops
it; `"sponsorship": "yes"` becomes a "Sponsors visa" card badge. Daily volume
target ≈40 via `BATCH_TARGETS`. Dedup uses `normalizeTitle()` (drops "(4+
yrs)", "(Remote)", req codes). `POST /api/jobs` refuses to create a copy of a
job already on the board (returns `duplicate: true` + message), and adopts a
hidden Job Watch copy as a manual job (`claimAsManual`) so it reappears.

**Countries:** every job has a `country` (default `HOME_COUNTRY` = "United
States"). The header "Region" picker filters the whole board — Board keeps all
API jobs in `rawJobs` and puts only the selected country's slice in `columns`,
so drag indexes and `KpiStrip` are per-country; new manual jobs get the
selected country; the detail panel can move a job between countries. Job
Watch runs ONE merged `home` batch (~25 per run) plus one `international` batch per
country in `search_preferences.job_watch_countries` (~15 each, local
work-permit rules via `visaRule()`), at most `MAX_PARALLEL_BATCHES` CLI
sessions at once. The senior-title filter applies to every auto-discovered
source (Job Watch, LinkedIn, Indeed), not just Job Watch.

**Company variety:** without this, a handful of large employers dominated
the board (five of them reached 41% of all jobs), so `homePrompt()` puts BROAD DISCOVERY before the
target-company sweep, only sends a `rotatingSample()` of `TARGETS_PER_RUN`
(18) companies from the ~107-entry list each run, and `OUTPUT_FORMAT` caps
results at 3 per company and requires half from employers not already seen.
`discoveryQueries()` varies modifier + region wording per run. Entries
starting with `//` in the company list are group headers and are filtered out
before sampling.

**One session per search, by design:** the home-country search used to be
three CLI sessions (priority / targets / tracked) that re-searched the same
companies and burned through Claude usage for no extra results. `homePrompt()` is now a single
session doing priority -> targets -> broad searches -> (only if short)
leftover tracked companies, with each company searched once. Keep it that
way: session count is the dominant cost, not prompt size. The ⭐ Priority
badge now comes from `matchesAnyCompany()` against the priority list rather
than from which batch found the job.

**Wishlist multi-select:** `selectable` is passed to `Column` for the
`wishlist` status only, which renders a checkbox + hover trash icon on each
`JobCard` and a "N selected / Select all / Delete" bar in the column header.
Selection state (`selectedIds`) lives in Board and is cleared on country
change. Both controls sit in an absolutely-positioned wrapper with
`onPointerDown`/`onClick` stopPropagation — without that, dnd-kit's listeners
on the card root would start a drag and the card's onClick would open the
detail panel. Bulk delete is `DELETE /api/jobs` with `{ids}` -> `deleteJobs()`,
which calls `deleteJob()` per id inside one transaction, so every removed job
is recorded in `dismissed_jobs` exactly like a single delete.

**Deleted jobs never come back:** `deleteJob()` writes the job into the
`dismissed_jobs` table first. `isDismissed(company, title, url)` (matching by
URL or normalized company+title) gates **both** discovery paths — the hourly
connectors' filter and `runJobWatch`'s ingest loop — and `listDismissedRoles()`
feeds a "NEVER suggest these again" block into every Job Watch prompt. Adding
the same job back by hand calls `undismiss()`, so the block is per-decision,
not permanent.

**Job Watch cadence:** manual by default — both `job_watch_times` (US) and
`job_watch_times_intl` (international) ship EMPTY, so nothing runs unless the
user clicks "Refresh jobs" (which forces every scope). Claude usage is the
binding constraint; don't reintroduce a default schedule. If times are set, they are comma-separated local `HH:MM` per scope. `dueScopes()` checks each scope against the most recent slot
that has already passed today (`lastElapsedSlot`) versus that scope's own
last success in the `scope_runs` table — so a slot missed while the app was
closed fires on the next open instead of being skipped, and the US schedule
never drags the international searches along. Empty = manual only. The board
POSTs `/api/job-watch` on mount (runs only the due scopes), the hourly
instrumentation timer pings it, and "Refresh jobs" sends `{force: true}` to
run every scope. `global.__jobWatchRunning` prevents overlapping runs.

**Board layout:** the board is pinned to the viewport (`h-screen`,
`overflow-hidden`) — the page never scrolls; each Column's card list is its
own `overflow-y-auto` scroll area. Keep `min-h-0` on the flex ancestors or
the columns will grow past the screen again.

**Data layer:** `src/lib/{db,jobs,generations,profile}.ts` wrap a singleton
`node:sqlite` (`DatabaseSync`) connection ([src/lib/db.ts](src/lib/db.ts),
synchronous queries, cached on `global` across dev hot-reloads). We use
Node's built-in SQLite module (stable since Node 22.5+, hence the `engines`
field in `package.json`) rather than `better-sqlite3` specifically to avoid
a native-compile dependency (node-gyp + a C++ toolchain) — keep that in mind
before reintroducing a native DB driver. `DatabaseSync` has no built-in
`.transaction()` helper (unlike better-sqlite3), so multi-statement moves
(`moveJob` in `jobs.ts`) wrap manual `BEGIN`/`COMMIT`/`ROLLBACK` via
`db.exec()`. There's no ORM — queries are plain SQL with named (`@field`) or
positional (`?`) parameters, both of which `node:sqlite` supports the same
way better-sqlite3 does — **except** named-parameter binding is stricter:
`StatementSync.run()`/`.get()`/`.all()` throw `"Unknown named parameter"` if
the object you pass has keys the SQL doesn't reference (better-sqlite3
silently ignores extras). This bit us once already — `updateJob()` in
`jobs.ts` used to spread the full existing row (`{...existing, ...input}`)
into a query that only bound a subset of those fields, and every status
change failed at runtime as a result. Always build the params object with
*exactly* the keys the query's `@name`s use, nothing more.
`listJobs()` includes a computed `has_generations` boolean (via `EXISTS`
subquery) used only for the small dot indicator on cards; `getJob()`/
`createJob()` don't include it.

**Types:** [src/types/index.ts](src/types/index.ts) is the single source of
truth for `JobStatus` (`wishlist|applied|interviewing|offer|rejected`) and
`GenerationType` (`cover_letter|resume_bullets|interview_questions|company_brief`),
including the arrays (`JOB_STATUSES`, `GENERATION_TYPES`) and label maps used
to drive UI iteration — the SQLite `CHECK` constraints in `db/schema.sql`
must stay in sync with these if either enum ever changes.

**UI conventions:** Tailwind only, no component library. Shared primitives
live in `src/components/ui/` (Button, Modal, Tabs, Input/Textarea, Spinner,
Badge, Toast, ArcReactor logo). The theme is a "JARVIS HUD" (Stark's
helmet/lab interfaces): holographic cyan line-work on navy-black, a faint hex
lattice backdrop, `.hud-frame` corner brackets on panels, squared-off
(`rounded-md`) shapes, outlined translucent buttons — tuned dim for long
sessions. Use the semantic tokens
from `tailwind.config.ts` (`bg-base`/`bg-surface`/`bg-surface-muted`/
`bg-surface-strong`, `text-ink`/`ink-soft`/`ink-muted`/`ink-faint`,
`border-line`/`line-strong`) — backed by CSS variables in `globals.css` —
never raw `zinc-*` or `white` surfaces, or that piece will render light on
the dark page. Accents: `accent` = HUD cyan (the system color: links,
highlights, focus, primary actions), `glow` = same cyan as CSS var, amber =
highlight/in-progress (priority, streak, interviewing), `suit` = alert red
(Rejected, delete), emerald = success; one signal color per pipeline stage in
`STATUS_STYLES` (`Column.tsx`). Keep glows small and low-alpha. `.glass` =
translucent panel; `.hud-frame` = corner brackets (background-image only, so
pair it with `.glass`/a bg color); `.text-gradient` = holographic cyan.
Headings/labels/counts/buttons use `font-display` (Orbitron); body text stays
Inter. Tailwind config changes need a dev-server restart to show up. Don't put a
`transform` hover effect on JobCard — dnd-kit drives its inline transform.
